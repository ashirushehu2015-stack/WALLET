## 1. COMPLIANCE BACKGROUND AND THREAT MODEL

The Nigerian Data Protection Regulation (NDPR) and Central Bank of Nigeria (CBN) security standards require strict confidentiality for Personally Identifiable Information (PII), particularly Bank Verification Numbers (BVN) and National Identity Numbers (NIN). 

### Threat Model
1. **Database Dump Exfiltration:** In the event of a raw database snapshot leak or unauthorized read-replica access, plaintext BVN and NIN values could be exposed.
2. **Log and Telemetry Ingestion:** Database queries and application error logs could accidentally log raw SQL strings containing plaintext identity data.
3. **Internal Privilege Escalation:** Database administrators or developers with direct SQL query access could view sensitive customer credentials.

---

## 2. CRYPTOGRAPHIC ARCHITECTURE SPECIFICATION

To resolve these threats, MangaPay implemented **Authenticated Encryption with Associated Data (AEAD)** using **AES-256-GCM**.

### Cryptographic Parameters
- **Algorithm:** AES-256-GCM (`aes-256-gcm`).
- **Cipher Key Length:** 256 bits (32 bytes).
- **Initialization Vector (IV):** 96 bits (12 bytes), generated independently for every encryption operation using `crypto.randomBytes(12)`.
- **Authentication Tag:** 128 bits (16 bytes), generated by the Galois Counter Mode engine to authenticate both ciphertext and metadata.
- **Key Versioning:** Prefix `v1:` prepended to every encrypted string to allow future cryptographic key rotations without breaking legacy records.

### Serialized Storage Format
```
v1:<12-byte-iv-hex>:<16-byte-auth-tag-hex>:<ciphertext-hex>
```
*Example:*  
`v1:3f2a89c4d11b5e78a9c011e2:7b88aa0912f54a8b9901ef23cba76541:89abcf...`

### Tamper-Proofing and Authentication
AES-256-GCM provides authenticated integrity. During decryption, the 16-byte authentication tag is supplied to `decipher.setAuthTag(tagBuffer)`. If an attacker or corrupt storage flips even a single bit of the ciphertext, IV, or tag, the cryptographic verification fails and throws:
`Cryptographic Decryption Error: Authentication tag mismatch or corrupt ciphertext`

Plaintext is **never emitted** if authentication tag verification fails.

## 3. DATA PRIVACY AND MASKING CONTROLS

To prevent sensitive identity exposure across application layers:

1. **Masking Utility (`maskIdentifier`):**
   - Retains only the last 4 digits of the 11-digit BVN or NIN.
   - Masks the leading 7 digits with asterisks: `*******4455`.
   - Supports both plaintext input and encrypted `v1:...` input (decrypts in memory, extracts last 4 digits, masks, and returns masked string).
2. **Controller and API Protection:**
   - In [`backend/src/services/kyc.service.ts`](file:///c:/Users/pc/Desktop/WALLET/backend/src/services/kyc.service.ts), `getMaskedKYCRecord(userId)` ensures that responses returned to the client frontend never reveal full identity numbers.
3. **Decryption Restriction:**
   - Plaintext access is strictly isolated to backend services requiring full numbers for provider communications (e.g., [`PaystackService.createDedicatedVirtualAccount`](file:///c:/Users/pc/Desktop/WALLET/backend/src/services/paystack.service.ts)).

## 4. SAFE DATABASE MIGRATION SCRIPT

A dedicated, idempotent migration script was engineered in [`backend/scripts/migrate-bvn-nin-encryption.ts`](file:///c:/Users/pc/Desktop/WALLET/backend/scripts/migrate-bvn-nin-encryption.ts).

### Migration Safeguards
1. **Idempotent Detection:** Uses `isEncrypted(value)` (`value.startsWith('v1:') && parts.length === 4`) to skip already encrypted records.
2. **Pre-Commit Roundtrip Verification:** Before issuing a SQL `UPDATE` for any record, the script executes `decryptIdentifier(newBvn)` in memory and asserts that the decrypted result matches the existing database value. If round-trip decryption fails, the migration halts immediately with no data loss.
3. **Batch Processing:** Processes records in batches of 100 within explicit transactions to minimize database locking.
